# Flood Label Reconciliation — Provenance and Decisions

Phases 4 and 5 of the evidence-based correction programme. Generated by
`ml/pipeline/p04_reconcile_labels.py`; the full per-event table is
`ml/labels/candidate_events.csv` (472 rows) and the accepted intervals are
`ml/labels/authoritative_events.csv`.

## Why this work was necessary

The forensic audit established, by direct cross-check, that **all nine independently
documented flood events in this project's own curated log are labelled `0` (no flood) in
the dataset the production model was trained and evaluated on.** It also established that
the label's coverage is non-stationary in a way that has nothing to do with Zambian
hydrology:

| Period | Reliable events in the baseline label | Plausible? |
|---|---:|---|
| 1990–1999 | 0 | No. Ten years, 27% of training rows, labelled entirely flood-free. |
| 2012–2014 | 191 / 233 / 219 | This is a DesInventar data-entry peak, not a flood peak. |
| 2018–2021 | 0 | No. The curated log documents eight events in this window. |
| 2024 | 0 | Unverified either way. |

The negative class therefore encoded *"no flood was recorded in DesInventar"*, not
*"no flood occurred"*. Because 99.8% of rows are negatives, that distinction propagates
into every reported metric.

## What was NOT done

- **No event was added without documentary evidence.** Every accepted positive traces to
  a named source and, where the source publishes one, a URL. Both are carried in
  `candidate_events.csv`.
- **No year-precision event was reinstated as a positive.** The baseline's decision to
  exclude them was correct and is preserved.
- **No false positive was relabelled.** The audit's hypothesis that some of the 88,184
  false alarms are unrecorded floods remains a hypothesis; none was promoted to a
  positive.
- **No label was changed to improve a metric.** The reconciliation is stricter than the
  baseline on 13 events and more complete on 60. It moves in both directions.

DFO and the curated log were already present in the project — DFO downloaded but never

`flood_events` table. Neither had ever reached the model's label.

## The third label state

The central correction. The baseline had two states; the corrected pipeline has three.

| State | Meaning | Used as |
|---|---|---|
| `flood_next_7d = 1` | a documented event falls in (t, t+7] | positive |
| `flood_next_7d = 0`, `label_usable = 1` | no documented event, and no documented uncertainty | negative |
| `label_usable = 0` | a source documents flooding in this location and window but not on which day, or not in which district | **neither class — excluded from training and from evaluation** |

Masking is the conservative half of the fix. It removes contaminated negatives **without
inventing a single positive the sources do not support.** A year-precision event is the
clearest case: the baseline labelled all ~365 days of that location-year negative, which
affirmatively contradicts the source. Those days are now excluded rather than asserted.

## Decision rules (Phase 5)

| Decision | Rule | Count |
|---|---|---:|
| `POSITIVE_DAY` | day-precision date, window ≤ 14 days, district named by the source | 282 |
| `POSITIVE_MONTH` | month-precision date, window ≤ 31 days, district named | 3 |
| `POSITIVE_DAY_ONSET_ONLY` | day-precision onset but window > 14 days — onset day positive, **remainder masked**, because the source does not document which later days flooded | 8 |
| `MASK_EPISODE` | flooding documented in a region/period but the district is unnamed, or a "month-level" range spans > 31 days | 13 |
| `MASK_YEAR` | year precision only | 163 |
| `EXCLUDE` | no parseable date, or no resolvable district or province | 3 |

**District attribution is exact, case-insensitive, word-boundary matching** of the 82
known district names against the source's own location text. No fuzzy matching. A district
is credited only when the source names it; unmatched text yields a mask, never a guess.

## Limitations that remain, stated plainly

1. **1990–1997 and 1999 still contain no documented district-level Zambian flood events.**
   No source currently in hand covers them. Those years' negatives remain unverified and
   are almost certainly still contaminated. They were **not** masked wholesale, because
   masking a decade on suspicion rather than evidence would itself be an unjustified
   assertion. The sensitivity of every result to including that era is reported separately
   rather than assumed away.
2. **2018, 2019 and 2024 remain empty.** ReliefWeb's API and EM-DAT would likely fill
   them; neither has been ingested.
3. **DFO events are regional.** Attributing them to districts by name match is defensible
   but coarse: a district named in a multi-district description may have been mentioned
   for context rather than flooded.
4. **Month-precision positives (3 events) label a whole month.** Flagged in the data by
   the interval's own `precision` field so any downstream analysis can exclude them.
5. **Flood mechanism is still not distinguished.** ZM-2021-01 is a dam-spillway failure
   triggered by rainfall, not pluvial or riverine flooding, and the curated log itself
   flags it as such. It is retained as a positive with that caveat recorded.
