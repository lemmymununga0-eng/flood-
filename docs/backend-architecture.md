# Backend Architecture — FloodShield Zambia

Status: real, running FastAPI backend against a real local PostgreSQL 16 database.
This document describes what actually exists as of this build (the "Complete Backend
Implementation & End-to-End Integration" master prompt, 2026-09-07), not an aspirational
target. See `docs/backend/frontend-integration-matrix.md` for the audit that preceded
this build and `docs/PROJECT-MEMORY.md` for the decisions behind it.

## Stack

FastAPI + SQLAlchemy 2.x (declarative `Mapped`/`mapped_column`) + Alembic (migrations)
+ PostgreSQL 16 + Pydantic v2 + python-jose (JWT) + `bcrypt` (password hashing, used
directly — see "Known deviations" below) + slowapi (rate limiting).

## Layout

```
backend/
  alembic/              # migration environment + versions/ (one baseline migration so far)
  app/
    core/
      config.py          # Settings (env-driven, no hardcoded secrets)
      security.py         # password hashing + JWT encode/decode
      deps.py              # get_current_user, require_roles (RBAC dependency factory)
      audit.py               # append-only audit-log writer
      pagination.py            # shared limit/offset query-param dependency
      rate_limit.py             # slowapi Limiter instance
      logging.py
    database/session.py    # engine, SessionLocal, Base, get_db
    models/                 # SQLAlchemy ORM models, one file per entity
    schemas/                # Pydantic request/response models
    api/                    # one FastAPI router per resource
    services/                # real external calls (NASA POWER ingestion, data-source health checks)
    main.py                  # app assembly: routers, CORS, exception handlers, lifespan
  scripts/seed_db.py          # idempotent real-data seeding (locations, flood events, roles, dev admin, data-source catalog)
  tests/
    unit/ api/ integration/ database/   # pytest suites, run against a real Postgres test DB
```

## Request lifecycle

1. CORS middleware restricts origins to `settings.cors_origins_list` (from `.env`,
   currently `http://localhost:5173` only — no wildcard).
2. Sensitive endpoints (`/auth/register`, `/auth/login`) are rate-limited via slowapi,
   keyed by client IP, in-memory (per-process — see "Known limitations").
3. Auth: a bearer JWT is verified by `app/core/deps.get_current_user` — decodes the
   token, checks `type == "access"`, loads the real `User` row from Postgres, rejects
   if missing/inactive. `require_roles(...)` wraps this to also check the user's real
   `Role.name` against an allow-list, per-endpoint.
4. Every raised `HTTPException`, validation failure, or unhandled exception is
   normalized by handlers in `main.py` into `{"error": <code>, "message": <text>}`
   (validation errors add a `"fields"` array with the real per-field detail).

## Authentication & RBAC

Real bcrypt-hashed passwords (via the `bcrypt` library directly — see deviation note
below), real signed JWTs (HS256, `settings.secret_key`), access tokens (30 min
default) and refresh tokens (7 days default, issued but not yet exchanged by a
`/auth/refresh` endpoint — see "Not yet built"). Five fixed roles — ADMIN, ANALYST,
OPERATOR, RESEARCHER, CITIZEN — stored in a `roles` table and seeded once by
`scripts/seed_db.py`; self-registration always assigns CITIZEN. RBAC is enforced via
FastAPI dependency injection (`Depends(require_roles("ADMIN", "ANALYST"))`) on:
alert creation, citizen-report moderation, and data-source health checks. Every other
endpoint (locations, flood-events, weather, predictions, system-status, model
registry, data-source listing, citizen-report submission/listing) stays publicly
readable, matching the dashboard's original public-read design — see the integration
matrix for the one deliberate behavior change (alert creation used to be anonymous).

## Database & migrations

Schema is now managed by Alembic (`backend/alembic/`), not `Base.metadata.create_all()`
— that call has been removed from `main.py`. One baseline migration
(`51f5e3fbdb3e_baseline_schema...py`) captures the full current schema (11 tables); it
was generated by dropping and recreating the dev database's `public` schema from
empty and running `alembic revision --autogenerate`, since no production data existed
yet to preserve. See `docs/database-schema.md` for the full table list.

## Testing

`backend/tests/` has four real suites (42 tests total, all passing as of this build),
run with `python3 -m pytest` from `backend/`:
- `unit/` — pure functions, no DB (password hashing, JWT encode/decode).
- `database/` — constraint enforcement at the schema level (unique/foreign-key
  violations actually raise `IntegrityError`), run against real Postgres.
- `api/` — one FastAPI `TestClient` per endpoint group, including RBAC
  allow/deny cases and the rate limiter itself.
- `integration/` — full multi-request flows (citizen submits a report → an operator
  moderates it → the change is visible on a subsequent list call).

Tests run against a **separate real PostgreSQL database** (`floodshield_zambia_test`),
never against the dev database — see `backend/tests/conftest.py` for the transaction-
per-test isolation strategy (SAVEPOINT restart pattern, so tests can call real
endpoints that `commit()` without leaking data between tests). Create it once with:
```
psql -c "CREATE DATABASE floodshield_zambia_test OWNER floodshield;"
```

## Known deviations from the master prompt's literal spec

- **Password hashing library**: the spec implies passlib/bcrypt; this build hashes
  passwords with the `bcrypt` library directly. passlib 1.7.4's bcrypt backend is
  incompatible with `bcrypt>=4.1` (a real `AttributeError` was hit and is documented
  in `docs/PROJECT-MEMORY.md`) — using `bcrypt` directly avoids that broken dependency
  chain while keeping real, industry-standard bcrypt hashing.
- **Roles as a table, not a fixed enum**: implemented as a genuine `roles` table
  (seeded, not user-creatable) rather than a hardcoded Python enum, so the schema
  itself reflects the "Roles" entity the spec lists — but there is no admin endpoint
  yet to grant/revoke roles; that requires a human operator running a script or a
  direct DB update (documented as a gap, not hidden).

## Not yet built (recorded, not silently dropped)

`POST /auth/refresh` (refresh tokens are issued but nothing consumes them yet), an
admin endpoint to change a user's role, SHAP-based prediction explanations (no trained
model exists), alert delivery to an external channel (SMS/email — no provider
configured), a shared/multi-process rate-limit backend (current implementation is
in-memory and per-process — fine for this single-process dev deployment, not for a
horizontally-scaled production one), and full e2e Playwright coverage of every user
journey (citizen/analyst/operator/administrator) — the citizen-report journey is
covered by an integration test; the others are not yet automated end-to-end.
