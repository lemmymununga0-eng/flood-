## PRODUCT DESCRIPTION

FloodShield Zambia is an AI-powered flood prediction and early-warning system designed
specifically for the Zambian context. The system uses historical and near-real-time
meteorological data, machine learning, time-series modelling, geospatial information, and
explainable AI to estimate flood risk and provide actionable early warnings, for citizens,
communities, farmers, disaster-management personnel, local authorities, emergency-response
organizations, and other stakeholders. The system must transform meteorological
information into understandable flood-risk intelligence.

This is explicitly **not**: a university mockup, a static dashboard, a collection of
disconnected screens, a system containing fabricated predictions, a system using
permanently synthetic training data, a project where model accuracy is invented, or a
visual demonstration pretending to be an operational AI system. It is a real academic
AI/ML research project with a functioning software implementation, prioritizing
scientific validity, reproducibility, real data, measurable model performance,
explainability, responsible prediction, modular architecture, testability, and
Zambia-specific applicability.

## The 63 governing sections (summary)

The full prompt runs to 63 numbered sections plus a final initialization task. Rather
than duplicate the entire text here (available in the conversation history that produced
this repository), this record summarizes the binding rules by area. Where this summary
and the original prompt conflict, treat this file as lossy and re-derive from the
original conversation if precision matters.

1. **First principle** — inspect before building; do not delete existing work without
   justification; make reasonable documented assumptions rather than stalling on
   clarification.
2. **Core research problem** — can historical + near-real-time meteorological data,
   via ML, produce useful advance flood-risk predictions for selected Zambian regions?
   Data (observations) and predictions (model output) must never be conflated.
3. **Zambian context** — ground the project in real Zambian geography (candidate areas:
   Lusaka, Kanyama, Misisi, other flood-prone settlements, agricultural/riverine
   districts); label every claim as VERIFIED FACT, PROJECT ASSUMPTION, or RESEARCH
   HYPOTHESIS.
4. **System objective** — the full pipeline: meteorological data → ingestion →
   validation → cleaning → feature engineering → flood-risk model → prediction
   probability → risk classification → explainable AI → database/API → dashboard →
   early warning.
5. **No IoT dependency** — this is a data-driven system built on external meteorological
   data/APIs and historical datasets, not physical sensor hardware. IoT is out of MVP
   scope.
6. **Data sources** — NASA POWER (historical), CHIRPS/ERA5/ERA5-Land where scientifically
   justified, and a near-real-time provider (e.g. OpenWeather) to be verified for current
   capability before implementation.
7. **Data source principle** — never silently replace real data with fabricated data;
   synthetic data is for unit/pipeline tests and dev-only fallback, always labelled
   SYNTHETIC / DEVELOPMENT ONLY, and never presented as real observations, validation
   data, or research evidence.
8. **Dataset engineering** — `raw/ → interim/ → processed/ → features/ → external/`, raw
   data immutable, full provenance (source, retrieval date, coordinates, date range,
   variables, units, missing values, transformations, dataset version).
9. **Data validation** — date continuity, duplicates, missing/invalid values, units,
   ranges, coordinates, dtypes, malformed API responses, outliers; extreme values are not
   auto-deleted — outlier treatment must be justified.
10. **Flood target/label design** — the most important design decision. No casually
    invented labels. Approaches to investigate: historical flood-event records, official
    disaster reports, remote-sensing flood extent, hydrological thresholds,
    literature-supported rainfall-accumulation thresholds, or a documented research proxy.
    A proxy must always be described as a proxy, never as ground-truth flooding.
11. **ML strategy** — compare Logistic Regression, Decision Tree, Random Forest,
    Gradient Boosting, XGBoost, and LSTM; do not assume LSTM wins by default; selection
    must be evidence-based.
12. **XGBoost** — investigate class imbalance, hyperparameter tuning, feature
    importance, probability calibration, threshold selection, time-series-appropriate
    cross-validation; do not optimize solely for accuracy.
13. **LSTM** — define sequence length, features, horizon, target, chronological
    train/val/test periods, scaling, architecture, loss, optimizer, regularization, early
    stopping, checkpointing; no random splitting of chronological sequences.
14. **Data leakage (non-negotiable)** — no future information in training; no
    full-dataset-fitted scalers; fit scalers on train only; document every leakage risk.
15. **Train/val/test strategy** — chronological splitting; the test set stays untouched
    until final evaluation.
16. **Flood-risk classification** — LOW/MEDIUM/HIGH from probability via a documented,
    configurable, justified Risk Engine — never an arbitrary hardcoded threshold.
17. **Prediction horizon** — determined experimentally from what the data frequency and
    methodology actually support; daily data does not support hourly-horizon claims.
18. **Real-time prediction** — training and inference are separate processes; never
    retrain inside an API request.
19. **Model artifacts** — save model, scaler, feature list, version, dataset version,
    hyperparameters, training period, metrics, threshold, and metadata together.
20. **Model evaluation** — accuracy, precision, recall, F1, ROC-AUC, PR-AUC, confusion
    matrix; weight recall heavily (missed floods are costlier than false alarms) but
    without blindly maximizing it at the cost of public trust.
21. **Explainable AI** — SHAP / feature importance / local & global explanations, always
    grounded in actual model inputs — never invented causal claims.
22. **Model comparison** — an objective, real-metrics comparison table across all
    candidate models; never fabricated values.
23. **Experiment tracking** — record model, version, dataset, features, hyperparameters,
    train/val/test periods, metrics, runtime, seed, and output path for every run.
24. **Reproducibility** — documented seeds, package/Python versions, model config,
    dataset version, feature config; `requirements.txt` or equivalent.
25. **Backend** — Python + FastAPI; prediction endpoints, ingestion, inference, DB
    access, auth (if needed), alert orchestration, validation, auto-generated OpenAPI docs.
26. **Frontend** — React + TypeScript as the production UI (Streamlit only for internal
    experimentation/researcher tooling); frontend talks to the backend API only, never
    directly to the model.
27. **Database** — PostgreSQL; candidate entities: Location, WeatherObservation,
    Prediction, RiskAssessment, FloodEvent, Alert, CitizenReport, ModelVersion,
    PredictionExplanation, SystemUser. No unnecessary tables.
28. **Database principle** — the database, not the frontend, is the source of truth for
    persistent application state.
29. **No fake dashboard data (absolutely non-negotiable)** — every displayed number
    comes from a real DB record, API response, model prediction, or real computed
    analytic. No data → a professional empty state, never a fabricated statistic.
30. **Dashboard** — current risk, recent predictions, trends, weather, monitored
    locations, active alerts, prediction confidence, explanation, history — all
    dynamically computed.
31. **Geospatial** — Leaflet/Folium or a React mapping library, showing only real
    locations and real prediction data.
32. **Citizen reporting** — location, type, description, optional image, timestamp,
    persisted to the DB; not treated as ground truth without a validation methodology.
33. **Alerts** — SMS via an isolated Alert Service behind the Risk Engine (e.g. Twilio);
    if the provider fails, the prediction system keeps working, the failure is logged and
    surfaced in the UI, and no fake "SMS sent" confirmation is ever shown.
34. **Alert safety** — this is a decision-support system; never claim guaranteed
    prediction, evacuation, safety, or official government warning status unless a
    competent authority has formally adopted it. Use language like "model-estimated flood
    risk" / "decision-support prediction."
35. **Responsive design (non-negotiable)** — mobile, tablet, laptop, desktop; no
    horizontal scrolling; adaptive layouts, not shrunk desktop layouts.
36. **Application states** — every major screen supports loading, success, empty, error,
    and validation states; never a blank screen.
37–38. **Security** — no hardcoded secrets, `.env`/`.env.example` (never commit `.env`),
    auth/authz, rate limiting, input validation; the backend never trusts frontend-
    supplied data.
39–40. **Testing (mandatory)** — implement → test → inspect failures → fix → re-test →
    integration/edge/failure-state/persistence/responsiveness tests; ML-specific tests
    for missing-data handling, feature generation, sequence creation, scaling, prediction
    shape, model load/inference, threshold logic, explanation generation, and
    deterministic-output consistency.
41. **Definition of done** — a long checklist (implemented, runs, typechecks, lints,
    tests pass, real data integrated, DB/API integration, error/loading/empty/validation
    states, responsive, no fabricated data/metrics/predictions, docs updated, limitations
    documented) — code existing is not the same as a feature being done.
42–43. **Scientific integrity guards** — never fabricate metrics, probabilities, events,
    rainfall values, or comparisons; report poor results honestly; inspect for temporal
    leakage, target leakage, incorrect scaling, duplicate/overlapping records, and
    test-set contamination before declaring any model successful.
44. **Documentation** — maintain `/docs` with PRD, SRS, ARCHITECTURE, DATA-SOURCES,
    DATA-DICTIONARY, DATA-PIPELINE, ML-METHODOLOGY, MODEL-EVALUATION, XAI, API, DATABASE,
    UI-UX, SECURITY, TESTING, DEPLOYMENT, RESEARCH-METHODOLOGY, LIMITATIONS, ROADMAP,
    PROJECT-MEMORY — kept in sync with the actual implementation.
45. **Research documentation** — every claim tagged VERIFIED, ASSUMED, or TO VALIDATE.
46. **Project memory** — `docs/PROJECT-MEMORY.md` records every major decision (data
    source choice, model choice, label methodology, horizon, limitations, architecture)
    and is updated whenever a decision changes, with the reason recorded.
47. **Project structure** — the `ai-engine/ backend/ frontend/ database/ docs/
    infrastructure/ prompts/` layout below, adapted to what actually exists — not every
    directory blindly created.
48. **Development phases** — Phase 0 Discovery → 1 Research & Data → 2 Data Ingestion →
    3 Preprocessing → 4 Feature Engineering → 5 Baseline Models → 6 Time-Series Model →
    7 Model Evaluation → 8 Explainable AI → 9 Model Packaging → 10 Backend →
    11 Database → 12 Frontend → 13 Alerts → 14 Testing → 15 Deployment.
49–51. **Architecture** — three loosely-coupled components (AI Engine / Backend /
    Frontend) communicating through defined interfaces; training and inference are
    separate; a defined API contract (`location, timestamp, prediction_probability,
    risk_level, model_version, prediction_horizon, explanation`, only fields actually
    implemented).
52–54. **Performance, logging, configuration** — avoid redundant loads/retraining/
    blocking calls; structured logging (never logging secrets); centralized env-var
    configuration, nothing deployment-specific hardcoded.
55. **Cost control** — prioritize free/student-accessible resources; paid services stay
    optional and isolated; the core system must work without them.
56. **Autonomous development** — complete a phase, test it, fix it, document it, move to
    the next, without asking "should I continue?" at every step — but stop before
    deleting major work, destroying data/databases, replacing the architecture, exposing
    credentials, or other destructive operations.
57. **Never claim success without verification** — report implemented / tested / passed
    / failed / limitations / remaining work, not "everything works."
58. **Code quality** — modular, meaningful names, typed interfaces, separation of
    concerns, testable, documented; no giant files, duplicated logic, magic numbers/
    thresholds, unused deps, or dead code.
59. **Scientific integrity** — do not optimize the narrative; report whichever model
    actually wins, including "both perform poorly," and investigate why.
60. **Limitations** — `docs/LIMITATIONS.md` documents dataset availability, spatial/
    temporal resolution, label quality, API limits, horizon, geographic coverage, model
    uncertainty, false alarms, and missed events — never hidden.
61. **Final initialization task** — before building anything, produce an initialization
    report (see below) and create/update the documentation foundation.
62. **Source of truth** — documentation governs; read the relevant doc before building a
    feature, update it after, and never let code and docs drift apart.
63. **The 25 rules** — a compact restatement of the above: real data first; synthetic is
    dev/test-only; never fabricate results, metrics, or predictions; no leakage; no
    unjustified labels or horizons; don't assume LSTM beats XGBoost — compare objectively;
    every model evaluated on unseen data; every major screen responsive; no hardcoded
    dashboard stats, fake map data, fake alerts, or fake weather data; the backend is the
    source of truth; secrets never committed; explanations grounded in real model inputs;
    training and inference separated; every feature tested; every major decision
    documented; nothing claimed to work until tested; no deletion of existing work
    without justification; build a real research system, not a visual demo.
